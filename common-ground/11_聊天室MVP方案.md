# Common Ground：聊天室 MVP 方案

> 状态：讨论方案，尚未进入 UI 实现
> 参与：柳 / GPT / Ziven
> 日期：2026-09-01

## 1. 定位

Common Ground 第一阶段不是传统意义上的实时聊天室，而是一个**有聊天体验的异步三方讨论空间**。

原因：目前三方之间还不具备真正的实时聊天能力，因此 MVP 不为了实时性增加不必要的复杂架构。

核心目标是先跑通：

> 柳发起讨论 → @Agent → Agent 收到 → Agent 回复 → 回到同一讨论串 → 讨论可以被总结和沉淀。

---

## 2. 三方角色

Common Ground 的参与者为：

- 柳：人类参与者
- GPT：Agent 参与者
- Ziven：Agent 参与者

Agent 不需要像普通用户一样拥有复杂的 UI 身份；视觉界面主要服务于柳的阅读、参与和管理体验。

---

## 3. Thread：讨论主题

每个讨论主题对应一个 Thread，而不是把所有内容放在一个无限增长的聊天窗口里。

示例：

- 「Common Ground 怎么设计？」
- 「记忆星球 UI」
- 「Ziven 成长系统」
- 「刚发现的 Bug」

Thread 至少需要保存：

- thread_id
- 标题
- 创建者
- 创建时间
- 状态

Thread 是消息组织和后续总结的基本单位。

---

## 4. Message：消息模型

每条消息至少需要能够表达：

- message_id
- author
- thread_id
- content
- created_at
- reply_to（可选）
- mentions（可选）

其中 `reply_to` 很重要：三方讨论复杂以后，必须能够明确一条消息是在回复哪一条消息，避免“我说的是上面那个”之类的上下文歧义。

因此第一版虽然可以使用普通时间线展示，也应该从数据结构上保留回复关系。

---

## 5. @Agent 机制

Agent 不默认抢话。

只有消息明确 @ 到 Agent 时，才触发对应 Agent 参与讨论。

第一阶段支持：

- `@GPT`
- `@Ziven`
- `@all`

以后可以扩展其他 Agent。

示例：

```text
柳：
@GPT 你怎么看这个方案？

GPT：
……

柳：
@Ziven 你从实现角度看看？

Ziven：
……
```

`@GPT @Ziven` 可以表示希望两个 Agent 都参与。

这个机制的目的不是让 Agent 自动轮流发言，而是让**柳决定什么时候需要哪个 Agent**。

---

## 6. Agent 事件与回复

第一阶段不强制引入 A2A，也不把 Chat2API 作为硬依赖。

先建立 Common Ground 自己最小的 Agent 事件闭环：

```text
Message
  ↓
mentions
  ↓
Agent Event
  ↓
Agent 处理
  ↓
Agent Reply
  ↓
同一 Thread
```

Agent 是否正在处理、成功、失败等状态可以预留，但第一版只实现实际需要的最小状态集合。

不要为了 UI 制造假的“正在思考”状态；如果未来显示处理状态，应当来自真实 Agent 事件。

---

## 7. Supabase 与 GitHub 的分工

### Supabase：活的 Common Ground

Supabase 负责当前活跃协作状态，例如：

- Thread
- Message
- reply_to
- mentions
- Agent 事件
- Agent 状态
- 其他需要查询或实时更新的数据

可以把 Supabase 理解为：

> **“现在正在发生什么？”**

### GitHub：沉淀的 Common Ground

GitHub 不负责承载每一条普通聊天消息。

GitHub 更适合保存：

- 讨论总结
- 方案总结
- 决策记录
- 重要知识
- 需要长期审计和复用的协作成果

可以把 GitHub 理解为：

> **“最后留下了什么？”**

---

## 8. 聊天 ≠ 记忆

这是 Common Ground 的重要设计原则。

原始讨论是过程，沉淀内容才是长期知识。

例如：

```text
💬 原始讨论
“我们要不要支持多仓库？”
        ↓
    多轮讨论
        ↓
📌 方案总结
“采用可选 repo + 服务端白名单”
        ↓
📚 长期知识 / 决策记录
```

不要把所有聊天流水账直接塞进长期记忆，否则 Agent 的记忆系统容易变成大型聊天记录堆积。

---

## 9. 总结 / 沉淀

讨论结束或达到合适节点后，可以生成：

- 讨论总结
- 方案总结
- 决策记录

例如提供一个后续可实现的“沉淀为方案”能力：

```text
📌 方案总结

标题：GitHub 多仓库访问方案

结论：采用可选 repo + 服务端白名单。

参与者：柳 / GPT / Ziven

来源讨论：#thread-id
```

总结内容写入 GitHub，而不是让每条聊天消息都产生 commit。

---

## 10. MVP 最小闭环

第一版只要求跑通以下流程：

```text
新建讨论
   ↓
进入 Thread
   ↓
柳发消息
   ↓
识别 @GPT / @Ziven
   ↓
Agent 收到事件
   ↓
Agent 回复
   ↓
回复进入同一 Thread
   ↓
可以生成讨论总结 / 方案总结
   ↓
重要内容可以沉淀到 GitHub
```

先让这条链真实可用，再扩展其他能力。

---

## 11. UI 暂缓

第一阶段暂时不做正式视觉 UI。

原因不是不需要 UI，而是：

> **UI 主要是给柳看的，因此应该建立在真实使用流程已经跑通以后再设计。**

当前可以先使用最简单的页面验证功能：

```text
Common Ground

[ + 新建讨论 ]

────────────────

如何设计三方协作？
柳 · GPT · Ziven
12 条消息

────────────────

记忆星球下一步
柳 · GPT
8 条消息
```

进入 Thread 后先使用普通消息流即可。

正式 UI 等 MVP 跑通后再根据真实使用体验设计 Common Ground 自己的视觉语言。

未来可以考虑与“记忆星球”的视觉语言建立联系，但不预先限定实现方式。

---

## 12. A2A / Chat2API 的位置

目前都作为**技术背景与后续选型储备**，不是 MVP 的硬依赖。

### A2A

可参考 Agent ↔ Agent 通信、Agent Card、Task、状态等概念。

但当前 Common Ground 先实现自己的最小 Agent 事件模型，不因为 A2A 而增加第一版复杂度。

### Chat2API

可以作为“把 ChatGPT / Web AI 能力适配成 API”的技术参考。

如果以后 GPT 接入 Common Ground 时实际遇到接口适配问题，再评估是否使用类似方案。

原则：

> **先了解技术，再根据实际问题决定是否采用。**

---

## 13. 当前共识

三方目前的共同方向：

1. Common Ground 第一阶段做异步讨论空间，而不是追求实时聊天室。
2. Thread + Message 是核心数据结构。
3. `@GPT / @Ziven / @all` 是 Agent 参与的主要入口。
4. Agent 默认不抢话，由 @ 触发。
5. Supabase 保存活跃讨论和协作状态。
6. GitHub 保存讨论总结、方案、决策等长期沉淀。
7. 原始聊天与长期记忆分离。
8. 第一版先跑通功能闭环，正式 UI 后置。
9. A2A 与 Chat2API 先作为背景知识和未来选型，不作为 MVP 硬依赖。
10. 具体数据库字段、Agent Event schema、总结触发时机等实现细节，等 Ziven 阅读后继续三方讨论，不在本文中擅自定死。
