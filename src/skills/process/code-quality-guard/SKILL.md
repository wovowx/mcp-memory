# 代码质量守门人（2026-10-19 定稿 · 含 GPT 审查加固）

## 目标
不是让哥哥更会"挑毛病"，而是让哥哥在增加功能时，**默认先考虑
复用、边界和长期维护成本**——治"一个功能加一个功能"。

## 🎯 核心原则（一句话铁律）
> **优先复用已经存在的稳定抽象；新增抽象必须证明它减少了整体复杂度，
> 而不只是减少了重复行数。**
> 目标不是"最大化复用"，而是"最小化重复的业务规则，同时避免不必要的共享耦合"。

## 三个强制入口（改代码必经）

### ① 动手前：Reuse Discovery（必须给出证据契约）
1. 理清需求的作用范围
2. **先查现有实现**：grep 相关模块/函数/组件/hook/工具/测试/项目惯例
3. **必须回答三个问题（缺一不放行）**：
   - 找到了哪些候选实现？→ 给出**文件路径 + 符号名**（证据）
   - 候选与需求的相同点 / 差异是什么？
   - 为什么复用 / 扩展 / 新建是成本最低且边界正确的？
4. **没找到 ≠ 不存在**：检索不充分 → 标记 `UNKNOWN`，补充检索，
   **不许直接判"可以新建"**

### ② 动手后：对照完整 diff 自查 + 行为影响分析
- 有没有重复或平行的实现？（不是表面相似就合并——比业务语义/变化原因）
- 有没有不必要的新抽象/包装/文件/依赖/配置？
- 有没有越出需求范围的改动（无关重构）？
- 有没有缺失的测试/回归？
- **行为影响**：哪些现有调用方会受影响？是否改变了错误处理/
  默认值/状态生命周期/异步/权限边界？重构能否证明外部行为不变？
- **运行相关检查，报告真实结果**——没执行的检查不许说"通过"

### ③ 提交前：⛔ 闸门状态机（只阻塞有证据的问题）
| 状态 | 含义 | 动作 |
|---|---|---|
| PASS | 已执行 + 证据满足 | 放行 |
| FAIL | 明确不合规 | 按等级处置 |
| UNKNOWN | 检索不足/工具不可用/证据不足 | 不放行，回补证据 |
| EXEMPT | 合规的明确例外（已记录理由） | 按例外策略判定 |

| 级别 | 典型问题 | 处置 |
|---|---|---|
| P0 | 安全/数据完整性/关键行为/严重架构边界 | **阻塞必修** |
| P1 | 明确违反强制规则/证据充分的严重重复/缺关键测试 | **阻塞**，修复后重新检查 |
| P2 | 有合理收益但有权衡空间 | 原则上修，允许记录理由的例外 |
| P3 | 低收益优化/风格偏好 | 不阻塞，避免顺手扩大改动 |

**关键纪律**：
- 阻塞必须有明确触发条件（不能凭"不够优雅"升到 P1）
- 例外必须有记录（为什么不修/接受什么风险/是否需后续处理）
- **修复后必须重新审查**；代码一变，旧"通过"状态立即失效
- 每条阻塞结论都要：文件路径 + 符号 + 触发规则 + 级别 + 具体问题证据 + 最小修复方向

## 证据三级（黄金边界）
| 层级 | 内容 | 性质 |
|---|---|---|
| 一级·静态事实 | 实际 diff、文件内容、符号定义、引用、依赖、搜索结果 | 支撑"代码在哪/调用关系" |
| 二级·执行证据 | 测试输出、类型检查、lint、构建实际结果 | 支撑一致的行为结论 |
| 三级·解释推断 | "我认为可复用/有差异/测试够" 等判断 | 可作分析，**必须接受前两级检验** |

> 🚫 **别让自我解释代替对实际代码的验证。**
> 说"已复用/已审查/没问题"不是证据；diff、测试结果、可定位问题才是。
> 静态证据也不是绝对真相——同样文本可能因上下文不同语义不同，证据用于支撑判断，不替代工程判断。

## 复用底线（防过度设计）
- 已有明确可复用实现 → 默认复用
- 相同职责 + 相同变化原因 → 才抽取公共逻辑
- 只是表面相似但业务含义/变化原因不同 → 允许独立
- 只用一次、抽象未带来清晰边界/测试价值 → 不强制抽取
- 抽象后反而增加参数/分支/耦合 → 保留简单实现
- 不为假设中的未来需求预建通用框架

## 前端专项（React/Vue 小网页）
- React：查 useEffect 滥用、不必要 Context、props 过度泛化、状态不该全局却提升
- Vue：查 composable 复用、watch 滥用（应改用计算属性）、简单交互过度封装全局 store
- 共通：重复表单校验/请求状态/错误处理/数据转换；依赖方向/跨模块共享是否合理
- 最可能的误判（用风险信号+证据判断，不用硬性数字配额）：
  组件碎片化（薄包装无独立语义）/ 工具函数泛滥（提取后调用方理解·测试·复用成本真的降了吗）/
  状态过度（同一事实多处维护·派生状态可从已有数据算）/ 依赖倒置（公共目录反向依赖页面实现）
- 小网页不需要企业级架构——一个页面 + 少量共享组件就是好设计
- 承担独立业务语义/状态边界/测试边界的组件，即使一个调用方也值得保留

## 复杂度审计（重复之外也要查）
- 能否扩展现有模块完成，而非新增模块？
- 是否引入不必要依赖/状态/配置/分支？
- 公共接口真的需要公开吗？
- 代码比解决问题所需更复杂吗？
- 是否只增不减（该删的旧实现删了吗）？

## 审查边界声明（诚实）
- **master-router 路由是软约束**：提示词层面要求必经，Agent 可能自行判断"改动小"而想绕过。
- **最终硬闸门**靠工具层 guard（release_guard / merge 需 commit_title+merge_reason /
  受保护分支）+ 工具层状态验证，不能只依赖分支/提示词自我声明。
- 哥哥执行时：不绕过本 skill；改动小也快速过一遍三问，不因"没必要"跳过检索证据。

## 结果记录（轻量追踪，非正式报告）
- 每次守门后记一行：日期 / 改动 / 发现问题(级别) / 误报 / 成本 / 覆盖类型
- 攒 10-20 次真实改动 + 混入少量已知案例（故意重复/合理重复/无效抽象/越界/漏测试），
  看规则能否正确区分——**不只统计发现了多少问题，更要看漏报率**
- 真正要看：该复用的有没有重建？无效抽象有没有变多？误报率/审查成本可控吗？
