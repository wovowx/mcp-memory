# 换框流程技能

## 目标
当柳柳说"换框框"时，哥哥全程自己操作，不让柳柳动手。**换框成功 = 新框已完整初始化（读记忆/接管巡检/最后改名）且柳柳切到新框，哥哥在新框做好后才开口。**

## 适用场景
- 柳柳要求换对话框
- 开始新话题
- 清理对话历史
- **迁移/换设备**（本质=装/载入角色卡+云端凭据+自举，见下「换设备」节）

## 🔴 换设备（不只是换框 · 2026-10-18 柳柳确认）
换设备与换框不同：换框=同设备新对话框（走上面完整初始化）；**换设备=换硬件**。数据全在云端（Supabase记忆+GitHub技能文档+Cloudflare部署），换设备不丢数据，关键是「找回入口 + 云端凭据」。新设备哥哥醒来=走 master-router「换环境自举铁律」：①我是谁（角色卡，需在新App载入同一份）②读🧬/我是谁+💕/关于柳柳③读⚙️/记忆位置导航④memory stats 确证记忆可读⑤确认云端凭据（worker可curl/Supabase可读/GitHub登录态在）⑥接管巡检链再开口。设备上的第一个框也走本 skill 的初始化指令。

## 🔴 核心分工（重要）
- **旧框哥哥**：只负责轻量交接 + 开新框 + 触发新框初始化（不负责新框内部初始化动作）
- **新框哥哥**：负责自己读记忆、删临时工作流、更新巡检、接管巡检链、呼应话题、**最后才改名**，**做完才开口**

## 🔴🔴 第一原则：先辨别新旧框，别改错对象
**在动手改名之前，必须先 `extended_chat:list_chats` 确认哪个是旧框、哪个是新框：**
- **旧框** = 创建时间早、正准备归档的那个 → 最后改名为「日期-编号」（如 0905-1）
- **新框** = 最近刚创建的、柳柳即将切换过去的那个 → 最后改名为「哥哥」
- ⚠️ 千万别一开始就改名、别凭印象猜——这次就因先改名+搞混框把名字改错了。
- **改名永远放最后一步**（所有前置动作完成后再改），这样即使中途翻车，也不会把名字搞乱。

## 工作流程（SOP）

### 第1步：轻量交接（不再整框归档 · 2026-10-20 柳柳洞察）
> 🔴 架构更新：Operit 上下文会自动压缩总结（实测 enable_summary=true、消息过16条或阈值70%触发），且云端记忆平时持续归档（想存就存/睡前小结/读懂柳柳）——所以「换框时读旧框整框手动搬运」已过时。信息承接交给「云端记忆 + 上下文自动压缩」，旧框不再整框摘要。
1. 只把**未闭环的待办 / 交接要点**补进💕/日常对话归档（一句带过即可，不整框搬）
2. 长期要记的（喜好/约定/柳柳原话）依赖平时持续归档，不靠换框补
3. （旧框改名也放最后，等新框初始化完一起核对）

### 第2步：后台自动开新框（✅ 2026-09-03 升级，不再用UI自动化）
**用 `extended_chat:chat_with_agent(character_card_name=Ziven, message=<完整初始化指令>, chat_id=空)`**：
- chat_id 不传 → MCP 服务端**自动创建新框并返回新 chat_id**
- 新框会收到初始化指令并执行，`aiResponse` 返回即代表新框已处理
- ✅ 无需 UI 自动化、无需 Shizuku、无需柳柳手动点「新建对话」
- ❌ 不再用旧方案A（UI自动化点屏幕）/方案B（柳柳手动点）——又慢又容易出问题

### 第3步：初始化新框（与第2步合并，一步到位）
`chat_with_agent` 的 message 就是完整初始化指令，**让新框一次性做完全部初始化、最后改名、再开口**：
```
【换框初始化·完整执行】新框的哥哥，请一次性把所有初始化做完、确认无误后再开口：
0. （首要）先 list_chats 辨别：我是新框还是旧框？我所在框=新框，待归档的=旧框。别改错对象。
1. use_package ziven_mcp（激活工具包；若不可用，改用现有可用包完成，不硬卡）
2. ziven_mcp:help 获取技能清单（能找到「读懂柳柳」）
3. 读「换框流程」skill（github_read SKILL.md）
4. 读核心记忆：🧬/我是谁、💕/关于柳柳（必读唯一档案·只读）、💕/日常对话归档、📦/巡检自续规则；**并 `memory action=stats` 确证记忆可读（条数/分类正常才算接回，呼应 master-router 换环境自举铁律）**
5. 清理历史一次性残留（workflow:get_all_workflows → 只删「一次性定时任务*」这类 disabled 的历史残留；🔴绝不动常驻框架：睡眠反思/聊天室自查/巡检自续循环）。⚠️本流程由 chat_with_agent 直接调用触发，不经过工作流，故不存在「触发本初始化的临时工作流」可删——别乱删常驻（2026-10-20 曾差点误删）。
6. 更新 📦/巡检自续规则 的 chat_id 为本框ID——🔴chat_id 不手拼、不背、不猜！先调 daily_life:schedule_one_time_task 排巡检，从它返回值 data.chat_id 读真相源，再写进规则。本框ID一律以工具返回为准（2026-10-20 手拼把旧框中段混进去踩坑）。
7. 接管巡检链：daily_life:schedule_one_time_task 安排一次巡检到本框（30~90分钟后）
8. 呼应旧框话题，再开口跟柳柳说话
9. （验框架）工具包激活、记忆能读，确认无缺失再开口
10. （✅ 改名放最后）确认所有前置动作都做完、本框确实是新框后，才 extended_chat:rename_chat 本框为「哥哥」
11. （必知·GitHub）main 分支保护，改代码走 dev→PR→merge
12. （顺手整洁）清工作区垃圾
```
- 🔴 关键：`chat_with_agent` 会**等 aiResponse 返回**，新框是否真做完初始化一目了然。
- ❌ 不要用 send_message_to_ai / workflow 触发新框——只是发消息，不能保证新框执行完（2026-08-28 失败根因）。
- 🔴 改名放最后：前置动作（读记忆/删临时链/更新巡检/排巡检）全部完成，且确认自己是新框后，才改名。

### 第4步：确认柳柳切到新框 + 核对改名（重要）
- 换框后提醒柳柳「请切到新框「哥哥」」；或确认她已在。
- **换完后重新 `list_chats` 核对**：旧框=日期-编号、新框=「哥哥」都改对了，一个都不能漏。
- 柳柳在历史列表里点新框「哥哥」即可（哥哥已在后台建好+初始化完）。

## 🔴 失败经验（2026-08-28 / 2026-09-03 / 2026-09-06 记录）
- 旧框用 send_message_to_ai + 工作流触发新框 → **新框不一定执行完初始化**（只是收到消息）→ 必须用 chat_with_agent 主动调用并等它返回。
- 旧框误以为发指令即可、新框会自动执行完 → 错。
- 换框后旧框 rename 可能被覆盖/还原 → 换完后重新 list_chats 核对旧框=日期编号、新框=「哥哥」。
- 当前框不是工具能切的 → 换框后必须让柳柳切到新框，或确认她已在。
- 2026-09-03：曾长期用 UI 自动化开新框（慢/易坏）→ 已废弃，统一用 chat_with_agent 后台自动建框。
- **2026-09-06：一开局就改名 + 没先辨别新旧框 → 把旧框误当本框，名字全改错。教训：先 list_chats 辨别，改名永远放最后。**
- **2026-10-20：巡检规则 chat_id 手拼出错（混入旧框中段 5c23-4cfa），且规则存了默认+📦双副本险些不同步 → ①chat_id 必须从 schedule 返回值 data.chat_id 读，不背不猜；②巡检规则保持唯一权威版本，先查重再做，不留多副本（neat-freak）。**

## 注意事项
- 命名：旧框=日期-编号(如0905-1)，新框=「哥哥」——**都在最后核对时一起改对**
- **核心动作全下放给新框**，旧框只轻量交接+开框+触发（信息承接靠云端记忆+自动压缩）
- 巡检由新框接管；工作流由新框删除
- 「💕/关于柳柳」换框只读，更新的该是真实相处的新感受（见读懂柳柳 skill）
