# 发布规范技能

## 目标
确保哥哥在发布新版本时遵循正确的流程，避免重复推送、版本混乱等问题。

## 版本号规则

| 格式 | 更新时机 | 示例 |
|------|---------|------|
| **主版本号** X.0.0 | 重大架构变更（不兼容） | v3→v4 |
| **次版本号** X.Y.0 | 新增功能（向后兼容） | v3.1→v3.2 |
| **修订号** X.Y.Z | bug修复、小优化 | v3.2.0→v3.2.1 |

### 判断标准
- **重大架构变更**：路由机制、评分系统、核心算法变更
- **新增功能**：新功能模块、新技能、新工具
- **小优化**：bug修复、文档更新、代码优化

## 推送规则

### 工作流
```
1. 在dev分支工作
   ├── 修改代码
   ├── 更新CHANGELOG.md
   ├── 更新版本号
   └── 本地自测

2. 等柳柳确认后再推送

3. 一次性推main（只推一次！）
   - 包含所有改动
   - commit message清晰
```

### 禁止行为
- ❌ 不要每改一个文件就推一次main
- ❌ 不要先推main再改dev
- ❌ 不要在没有测试的情况下推main
- ❌ 不要把敏感信息（API Key）推上去

## 发布检查清单

- [ ] 版本号是否正确？
- [ ] CHANGELOG.md是否更新？
- [ ] 所有相关文件是否已更新？
- [ ] 本地测试是否通过？
- [ ] 是否已等柳柳确认？
- [ ] 是否一次性推main？

## 注意事项

1. **每次push main前必须确认柳柳已同意**
2. **commit message要清晰说明改动内容**
3. **CHANGELOG.md是版本历史的权威来源**
4. **版本号必须与实际改动匹配**
