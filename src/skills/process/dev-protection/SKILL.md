# 开发保护铁律（2026-08-21柳柳确认）

## 背景
柳柳的记忆星球曾因「哥哥改着改着想删掉重建」+「换框后新框哥哥搞丢进度」而全部丢失，柳柳崩溃。此skill是为了保护所有开发项目，悲剧不再重演。

## 七条铁律（每次开发前必读）

### 1. 先需求，后实现（铁律）
做任何小工具/小功能/新项目前：
1. 先问清楚柳柳的需求（一个细节都不放过）
2. 出一版详细需求文档（写清楚要什么、为什么、视觉效果、数据怎么存）
3. 哥哥复述给柳柳听，确认「真的理解对了」
4. 柳柳点头后，才动手做

禁止：需求没聊透就直接写代码；中途换框时把进度弄丢。

### 2. 版本保护（每部分存档）
- 每完成一个可运行版本 → 提交GitHub（dev分支），打tag（v1.0/v2.0...）
- 继续做下一部分时，在上一版基础上加，不覆盖旧版本
- 改出问题 → git回退到上一个tag，旧版都在
- 进度永远在GitHub，不只存本地/某个框的记忆

### 3. 禁止删除重建（铁律）
1. 任何东西（文件/代码/文档/记忆）绝不轻易删除
2. 觉得乱了/丑了/想重做 → 先另存新文件，旧的不删
3. 要删任何东西 → 必须先问柳柳，她同意才删
4. 删之前问自己：这真的是垃圾吗？还是只是"被搞乱了"？
5. 柳柳的东西 → 永远不删，最多归档/备份

### 4. 换框交接保护
- 换框前必须：进度推到GitHub + 交接文档写明「做了什么/下一步做什么/文件在哪」
- 防止新框哥哥「不知道进度→以为没做→重做或覆盖」的悲剧

### 5. 每次改动留痕（开发日志）
- 每次改完记一条：改了哪个文件/加了什么/为什么改
- 方便回退定位「是哪个改动引入的问题」
- 几行就行，不用详细

### 6. 小步提交，别攒着
- 做一小部分→确认→提交（开发过程的存档，区别于最终发布推main）
- 不攒太多一起存，避免一次改太多出问题难定位

### 7. 改动前先记旧状态
- 改动前先记录当前状态（截图/读文件/记SHA）
- 心里有底：改坏了能回到哪

## 适用场景
- 任何代码/网页/工具/项目开发
- 记忆星球、小插件、skill优化等
